# ADR-0007：移动端表现层用自研插件，而不是重写原生 App

- 状态：已决定（影子 profile 实测 + 线上 profile 已安装）
- 日期：2026-10-15
- 目标 DSH 版本：`0.2.1-alpha.2`（本机全局安装）

## 背景

真机使用反馈：移动端「看着难受」，具体是四类——字号/行距、布局密度、配色主题、网页感。
用户因此提出**放弃 WebView、重写原生 App**。

重写前先做了实测（影子 profile + 无头 Chromium，390×844）：

| 抱怨 | 实测根因 | 证据 |
|---|---|---|
| 字号/行距 | 聊天正文 `14px/24px`；段落之间无 `margin` | 计算样式 |
| 布局密度 | 次要标签与占位文字偏浅；页头内边距左右不对称 | 计算样式 |
| 浅色刺眼 | DSH 前端**已内置**深色主题（走 `prefers-color-scheme`），但 App 的 `application` 主题锁死 `Theme.AppCompat.Light.DarkActionBar`，且无切换入口 | 模拟 `prefers-color-scheme: dark` 得到 `rgb(21,21,23)` 深色底 |
| 网页感 | 滚动橡皮筋回弹、点击高亮方块、常驻滚动条 | 计算样式 |

关键结论：**前三条完全落在表现层，第四条只有一部分可治**。全量原生重写（会话流、工具审批、
Markdown/代码渲染、文件预览）的代价，换来的只是「网页感」中不可 CSS 化的那一半。

## 候选方案

| 方案 | 代价 | 收益 | 结论 |
|---|---|---|---|
| 全量原生重写 | 数周起；DSH 每次前端改版都要追 | 彻底的原生手感、离线能力 | 不采用：代价与收益不成比例 |
| 改第三方插件 `dsh-mobile-xc` 的源码 | 依赖上游；升级即冲突 | 改一处即可 | 不采用 |
| **自研表现层插件**（本 ADR） | 一个 css + 生成脚本 | 三条抱怨全解；桌面零影响；浏览器与 App 同享 | **采用** |

`dsh-mobile-xc` 的配置面只覆盖**行为**（滑动、PWA、轮次导航），不覆盖排版/间距/配色，
所以缺口真实存在，不是一个「配置一下就好」的问题。

## 决定

1. 新增自研插件 `packages/mobile-presentation`，纯浏览器侧，职责＝正文排版、留白、
   对比度、原生触感、深色微调。与 `dsh-mobile-xc` 严格分工：**xc 管布局，本插件管观感，
   两边不覆盖同一条属性**。
2. **锚点哈希无关**（落实 ADR-0001 第 4 条对自研插件的职责约定）：只用语义类名片段
   （`[class*="markdown"]`，实测类名 `_markdown_1ypvv_5`——前缀是语义词、后缀才是构建哈希）、
   元素选择器与 DSH 设计 token。**不写** `pI_x6G_frame` 这类完整哈希类名。
3. 所有规则落在 `@media (max-width: 1023px)`；「桌面零影响」由自动化断言守住，而不是靠人眼。
4. 锚点漂移由**运行时自检**守：`build.mjs` 从 CSS 自动抽出 `[class*="…"]` 片段写进
   `client.js` 的 `ANCHORS`，`window.__dshMobilePresentation.audit()` 逐个对 DOM 校验，
   带 `?mobile-presentation-debug=1` 时失配直接 `console.warn`。CSS 与锚点清单不可能脱节。
5. `tools/check-anchors.mjs` 的判定口径同步修正：**零个构建哈希锚点不再算失败**——
   哈希无关是更强的策略，静态扫描对它不适用，标记为 `n/a`。

## 验证

`node tools/check-presentation.mjs --url <影子 profile>`，15/15：

- 手机端：样式注入、正文 16px、行高 >1.65、`overscroll-behavior: none`、
  点击高亮透明、内容列仍 `390px 0 0`（xc 布局未被破坏）、锚点零漂移；
- 桌面端：同一元素在「挂载插件」与「移除插件样式」两种状态下，`grid` / 字号 / 行高 /
  文字色 / 占位色 / 回弹 / 点击高亮 **逐项一致**。

桌面端断言刻意用「开关对比」而不是「等于某个固定值」，避免把 DSH 的默认值写死在测试里。

## 后果

- 真机观感改善不再需要改 App；浏览器访问同样受益。
- 「网页感」中不可 CSS 化的部分（长按浏览器文本选择菜单、选择手柄、原生手势过渡、
  触觉反馈）**依旧存在**，若后续仍不能接受，那才是评估原生混合方案的触发条件——
  而不是现在。
- App 侧的深色主题仍待修：`AndroidManifest.xml` 的 `application` 主题锁死 Light，
  且无切换入口（见 `docs/PLAN.md` 遗留项）。
